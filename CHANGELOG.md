# Changelog

All notable changes to Sidekick will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [2.9.0] - 2026-09-05

### Added

- **Web UI bridge (`/sk webui`).** Off by default. When on, the addon writes a
  snapshot of this character's config to
  `config\addons\sidekick\<Name>_<ServerId>\state.json` once a second (only when
  something actually changed), a liveness `heartbeat.json` every ten seconds, and
  polls `request.txt` for instructions from the web app, answering in
  `response.txt`. There is no socket and no server: the browser holds a File
  System Access grant on the addon's own config folder, and addressing a
  character is writing to that character's folder. `/sk webui folder` prints the
  path to point the app at; `/sk webui open` opens the address in the
  per-character `webui_url` setting, and `/sk webui url <address>` changes it.
  The built-in default (`https://sidekick.workers.dev`) is only a placeholder:
  `wrangler.jsonc` names the worker but declares no route and no custom domain,
  so `wrangler deploy` actually publishes to
  `sidekick.<account-subdomain>.workers.dev`, and the subdomain is specific to
  whichever Cloudflare account it was deployed under -- this repo has no way to
  know it, so each player has to point `open` at their own with `/sk webui url`
  once.
- **Web app.** A hosted progressive web app (Chromium only — the File System
  Access API does not exist in Firefox or Safari) that draws the config window
  from the schema the addon exports: the same sections in the same order, with
  the same enable checkboxes, ability rows, ME/P1-P5 buff target buttons and
  sliders. A row of character buttons switches between every character logged in
  on the PC, with a live/offline dot driven by the heartbeat. The gear icon opens
  the job-independent settings that live in `/sk panel` in game — Multisend
  Follow, Hold AOE for Group, Pianissimo Fast Casting, Cast with 1 Shadow, Cure
  and Waltz potency, Song Duration, AFK Sleep and its timeout, UI opacity, Load
  stopped, Stop after zone, section display mode, and Attack Range when
  Multisend Follow is on. `/sk panel` itself is not reproduced.
- **Schema export (`lib/ui/schema.lua`).** The config window as data, mirroring
  `lib/ui/config.lua`'s order, labels, enable keys, defaults and visibility
  rules. It is the contract in both directions: the browser draws what is in it,
  and the addon refuses to set anything that is not in it — so a control the
  in-game window would not draw right now is not settable right now either.

### Changed

- Ability, group and buff-target changes from the browser go through the same
  toggle functions an in-game click uses, so the two-song limit, exclusive Geo
  targets and the `disabled_` key each row keeps in sync behave identically from
  either side.

### Fixed

- **Party-buff target selections now hydrate even if the config window is
  never opened** (`ui_config.hydrate_party_buffs`, `lib/ui/config.lua`,
  `lib/core/webui.lua`): the Buffs, Geo, Sleep Removal and Debuff Removal target
  rows were loaded from `settings.party_buffs` only inside `render()`, which
  runs solely while the config window is on screen, so a session that never
  opened `/sidekick` had those buffs silently not fire at all even though the
  saved targets were there. Hydration is now a shared function called from both
  `render()` and the web UI bridge's tick, so it happens regardless of whether
  the window — in game or in the browser — has ever been opened this session.

## [2.8.0] - 2026-08-31

### Added
- **Sections can render as a row of tabs instead of a stack of collapsing headers** (`components.lua` `begin_sections`/`begin_section`/`end_section`/`end_sections`, `config.lua`): the config window's sixteen main sections — Auto Follow, Pet Control, the healing and removal sections, Resting, Resource Recovery, Rolls, Buffs, Geo, Revive — now have two possible chromes, and exactly one is in force at a time. **Right-click any section header** for *Display as tabs*; **right-click any tab** for *Display as section headers*. The choice is the new per-character `display_mode` setting (`'headers'` by default), saved to the character's `settings.lua` alongside everything else, so it survives a reload and a job change. Thanks to **Bloodlust** for the feature idea.

  **Each tab carries its own enable checkbox.** ImGui can draw no widget on a tab, so the checkbox sits at the top of the tab's body, above a separator, and it renders even while the section is disabled — it is the only way to switch one back on. It writes the same setting the header-mode checkbox does, so the two chromes always agree. **Disabled sections' tabs are dimmed**, which is the enable state you can read without opening anything.

  The tab bar uses `FittingPolicyScroll`, so labels are never truncated and scroll arrows appear once sixteen tabs outgrow the window. It is submitted after the tracked-targets row, since ImGui allows nothing but tab items between `BeginTabBar` and `EndTabBar`. A mode switch is applied on the frame *after* the click: the popup that requests it opens inside a frame already begun in the old chrome, and switching on the spot would leave a `BeginTabBar` without its `EndTabBar`. If `BeginTabBar` ever refuses (a clipped window), that frame falls back to headers rather than rendering nothing.

  Internally this replaced `collapsing_checkbox_header` with a four-call section API, and the sixteen call sites in `config.lua` now read `ui.begin_section(...)` / `ui.end_section(...)` around bodies that were not otherwise touched. No automation behaviour changed.

  **Disabled sections sort after the enabled ones**, so the bar reads left to right as on, then off (`begin_section`/`end_sections`, `deferred_tabs`). A disabled section submits no tab where it is declared: it is held back and submitted after every enabled one, which costs nothing because the call site gates its body on `is_enabled` -- a disabled tab's entire body is the enable checkbox `begin_tab_section` draws itself. Its help text is carried along with it, since the `item_tooltip` that follows `begin_section` has no item of its own to attach to and would otherwise land on the previous tab.

  Submission order alone does not move a tab. **ImGui keeps a bar's tab order across frames** and only re-sorts it into submission order when a tab is *added*, and toggling a section adds nothing -- so a disabled tab's ImGui id now carries an `_off` suffix, which ImGui reads as the old tab closing and a new one opening, and the sort follows. That close would also drop the selection: ImGui answers a closed selection by falling back to the most recently selected tab, which is not where the user was standing in either direction. So the selection is driven explicitly (`reselect_id`, set by `set_section_enabled`, honoured by `begin_tab_section`). **Enabling** re-targets the section just switched on: its tab snaps into the enabled group and stays the open tab. **Disabling** re-targets `previous_section` -- the tab that was open before this one -- since the section's own tab is on its way to the disabled end. `ImGuiTabItemFlags_SetSelected` is re-submitted every frame until the target tab actually reports selected, bounded at four frames (`reselect_frames`) in case the target stops rendering mid-transition. That carries the disable case, whose target tab already exists. It does not carry the enable case, whose target is an id ImGui has never seen: the tab it would take the selection from is removed in the same layout pass, and the fallback wins the race. Enabling therefore also passes `ImGuiTabBarFlags_AutoSelectNewTabs` on `BeginTabBar` for the two frames the new tab takes to appear (`autoselect_frames`) -- ImGui resolves that one itself, and the toggled section is the only tab whose id changes on a toggle frame, so there is nothing else for it to catch. It is armed for enabling only; left on, it would hand the selection to the `_off` tab a disabling section creates.

  `ImGuiTabItemFlags_Leading`/`_Trailing`, which exist for exactly this, are not usable here: ImGui shrinks the leading and trailing sections to fit the bar once they no longer fit, and gives the central section whatever is left. With sixteen sections in a window sized to a 250px slider, either arrangement ends with one group of tabs squeezed down to nothing and unreachable -- and an unreachable tab is an unreachable enable checkbox.

- **The config window can be given a custom size** (`window_size_mode`, per character, `'auto'` by default; `config.lua`, `components.lua` `render_window_size_menu`/`apply_pending_window_size_mode`/`begin_opaque_context_window`): the window has always been pinned to its contents with `AlwaysAutoResize + NoResize`, which resizes instantly but cannot be adjusted. **Right-click any empty space in the window -- its body or its title bar, anywhere that is not a widget, a header or a tab** for *Use a custom window size*: the window keeps the size it currently has, gains a resize grip, and scrolls when the contents outgrow it. Right-clicking empty space again offers *Fit window to contents* to go back. The menu has the same shape as the display-mode menu it sits beside: the behaviour currently in force in gray, a separator, then a single item describing the switch, so it never asks the user to pick the mode they are already in. Thanks to **Toranko** for the feature idea.

  **The size itself is not a Sidekick setting.** ImGui already persists this window's size and position in its own `imgui.ini` — the same mechanism that keeps the window where you left it across job changes — so only the mode is written to the character's `settings.lua`. That also makes the switch to custom free of a "starting size" decision: dropping `AlwaysAutoResize` leaves the window at exactly the size the auto-fit had just produced, which is where the user wants to start dragging from.

  The popup opens on empty space only, via `ImGuiPopupFlags_NoOpenOverItems`, which is what keeps it clear of the display-mode popup on every section header and tab and of the per-target and per-ability popups on the rows inside. Both flag names, like every other ImGui enum this addon uses bare, come from the `require('imgui')` at the top of the file. A mode switch is applied on the frame *after* the click, through the file-local `pending_window_size_mode` and `apply_pending_window_size_mode` — the same one-frame defer `display_mode` uses, here because `imgui.Begin`'s flags and `SetNextWindowSizeConstraints` both have to be settled before the window opens and the click necessarily happens inside a window already begun. Custom mode floors the size at 320x200: ImGui's own `WindowMinSize` is 32x32, and while the right-click menu is still reachable there (the title bar opens it too), a window that small is unusable — the floor is comfort, not an escape hatch.

  Only the config window is affected. The floating widget (`/sk widget`) and the debug panel (`/sk panel`) keep their own auto-sizing.

### Fixed
- **Loading a settings profile no longer moves the window chrome around** (`PROFILE_EXCLUDED_KEYS` in `config.lua`): `ui_opacity`, `ui_open` and `widget_open` were being captured into every profile snapshot and applied back on Load, so switching profiles could fade the config window to a stranger's opacity, close it out from under you, or pop the floating widget open. They join the container/run-state/focus/follow keys the profile system already excludes, alongside the two new chrome settings `display_mode` and `window_size_mode` — none of these describe *what Sidekick does*, which is the only thing a profile is for. Snapshots saved before this change still carry the three keys on disk; they are now ignored on Load rather than applied, so no migration is needed.
- **Pet Debuff Removal now has hover help** (`tooltips.lua`, `config.lua`): it was the only one of the sixteen sections with no `item_tooltip` after its `begin_section`. The new text says what the section does and repeats the packet-inference caveat the per-ability tooltip already carries. The missing call was also a latent trap in tab mode: `begin_tab_section` samples the tab's hover into a file-local that only `item_tooltip` consumes and clears, so the first tooltip anyone added inside that section's body would have tested the tab's hover rather than its own widget's.
- **Erase's ailment list now mirrors the server's own erasable flag** (`ERASABLE_DEBUFFS`, `DEBUFF_NAMES` in `common.lua`): the list was hand-assembled and short, so Erase sat idle on statuses the server would have let it strip. It is now every `status_effects.sql` row carrying `EFFECTFLAG_ERASABLE` (0x2) — the only flag `EraseStatusEffect()` reads. Thanks to **Atsumu** and **Tai** for bringing the missing ones to my attention.

## [2.7.0] - 2026-08-17

### Added
- **Sleep Targets — the Sleep Removal section's target buttons are now labelled, and the section hides while solo** (`config.lua`, `components.lua` `render_party_selection`): Sleep Removal has always filtered on a per-target selection (`settings.party_buffs.wake`, read by `status_removal.execute_wake`), but the button row carried no label next to the labelled **Group Targets** / **AOE Targets** rows. It now reads `[P1] [P2] … Sleep Targets`, matching those two, and the tooltip says what the buttons do and that — unlike the session-only heal rows — these choices are saved. There is still no **ME** button: a sleeping player cannot cure their own Sleep. For that same reason the entire section is now hidden unless `common.get_party_size() > 1` — solo there is nobody to scan and the whole thing is dead UI. That gate also guarantees at least a **P1** button, so the label's `imgui.SameLine` needs no "did anything render" guard.

  **Damage-immune trusts are locked out of the row.** `common.is_trust_excluded`'s list (Moogle, Kupofried, Sakura, Star Sibyl, Brygid, Cornelia) takes no damage and no status, so they can never hold a Sleep to remove. Their button is now grayed and swallows clicks with a `<name>` / *Cannot be given a status ailment* tooltip, the same treatment they already got on the Group/AOE heal target rows and on buff rows. No matching skip was added to `execute_wake`: those trusts never carry the Sleep status in the first place, so the scan cannot pick them regardless.

  The gray/dim/tooltip button styling behind both target rows is now one file-local `draw_toggle` in `components.lua`, called by `render_party_selection` and `render_heal_group_selection` instead of being open-coded per button kind.

- **Scholar gets an AOE heal — Accession paired with a cure** (`scholar.lua` `abilities.heal_aoe`, `heal.execute_aoe`): Scholar has no Curaga line, so its only party-wide cure is **Accession**, the stratagem that makes the *next* single-target healing spell land on everyone in range. It is now wired as Scholar's `heal_aoe` entry and appears as a plain checkbox in the existing **AOE Healing** section, under the same **AOE (HP%)** threshold and **AOE Targets** selection every other job's AOE heal uses. When the threshold trips, `heal.execute_aoe` fires the JA and casts the cure on the follow-up tick, aimed at the lowest-HP member — Accession radiates from the *target*, not the caster, so the spell needs somebody to centre on and the range check is made against that member. The pairing is keyed off a new `aoe_precast` ability flag rather than off the job id, so a future job with the same shape gets it for free.

  **The cure is chosen before the JA fires**, which is the whole point of the ordering: `heal.select_ability` runs first against the job's own single-target heals, level-filtered and narrowed to the spells the stratagem can actually spread (`common.stratagem_applies` against the shared `spell_ids` allowlist, now hoisted to one file-local `ACCESSION_SPELL_IDS` in `scholar.lua` so the precast entry and this one cannot drift apart). A stratagem charge is therefore never spent on a tick where no cure could have followed it — silenced, on recast, out of range, or unaffordable. That last one is checked at the **doubled** cost Accession charges: on the tick that decides whether to fire the JA the buff does not exist yet, so `common.effective_ability_cost` has nothing to see and the candidate list is filtered inline against `math.floor(cost * mp_modifier)`. Without it Sidekick would budget a Cure IV at 88 MP, burn the charge, and then fail to cast the 176 MP spell it had just committed to.

  The pass runs in three steps. **Buff already up** (the follow-up tick, or the player pressed Accession by hand) casts the paired cure: the charge is already spent, so the gate is the looser "at least one member below threshold" rather than the full two-plus-average bar — but not zero, or a hand-pressed Accession would fire a cure into a full-HP party. Otherwise `action_core.first_command` over the non-precast entries runs, since a free Curaga beats a charge plus double MP. Only then is the JA fired, guarded on the buff *not* being up so a tick that fell through the first step can't spend a second charge on a buff already held.

  The follow-up is the *existing* stratagem lock, not a new mechanism: the JA result carries `is_stratagem`, so `automation.lua` re-runs only `heal_aoe` on the next tick and nothing can pre-empt the paired cure — which is why no cross-module "forced heal" flag is needed the way RDM's Convert needed one. That cure is cast **directly**, deliberately bypassing `common.check_stratagem`: a stratagem the user had assigned to Cure through the **S** popup would otherwise spend a *second* charge and break the lock. Bypassing it also skips the **Hold AOE for Group** gate that lives there, so the JA branch applies that check itself — Accession radiates `common.AOE_RADIUS` (10 yalms) from the cure's target, not the cure's own 20-yalm range, so without it a lone straggler 18 yalms out would eat the charge and the doubled MP by themselves. With the setting off (the default) behaviour is unchanged: fire, covering whoever is in range, like every other AOE in the addon.

  The entry carries **no `recast_id`** on purpose — 231 is a charge pool that counts down per charge rather than to zero, so `action_core.is_usable` would read a flat zero and pass at full charges only; charges are gated by `requires_stratagem_charge` through the job's `validate_ability`, exactly like the Addendums. That validator makes one exception for this entry: once Accession's own buff (366) is up the charge is already spent, so it stops charge-gating and lets the entry through the level filter — otherwise the very tick that spent the last charge would drop the entry, strand the cure, and let the lock time out. `heal_aoe_enabled` stays **off** by default for Scholar (it now means "spend a stratagem per party heal", which is a real cost), and an `aoe_precast` entry is split out of the list handed to `action_core.first_command`, so the bare JA can never fire as though it were the heal itself.  Thanks to **Toranko** for the feature idea.

- **Hold a Stratagem for AOE** (`stratagem_reserve_aoe`, per character, off by default): a right-click item on the Accession row in **AOE Healing**. With it on — **and only while AOE Healing is itself enabled** — one charge is fenced off for the AOE heal above and **every other stratagem consumer reads one fewer**, a lone charge reading as none, so an Addendum or a Penury'd cure can't quietly drain the pool that the party heal is waiting on. Backed by `common.spendable_stratagems(settings)`, which `common.check_stratagem` and Scholar's `validate_ability` now read in place of `game_state.stratagems`; the AOE heal is the reserve's own consumer and keeps reading the real count, and `/sk panel` keeps displaying the real count too. The `heal_aoe_enabled` half of the condition is load-bearing rather than defensive: with AOE Healing off there is nothing to reserve *for*, and the checkbox that clears the reserve sits on an ability row `config.lua` only draws while the section is open **and** enabled — so a reserve left set behind a disabled section would starve Addendum: White and every assigned precast indefinitely, with no visible control left to undo it. Scholar's `validate_ability` needed the settings table to see the toggle at all, so `common.filter_abilities_by_level` now passes it as a third argument (`validate_ability(ability, common, settings)`) — every other job's validator ignores the extra argument, so nothing else changes. The checkbox is added to the **existing** Combat Only / Idle Only context popup rather than a second `BeginPopupContextItem` on the same widget, since two popups on one item stack duplicate menus.
- **Shared party list — a second box picks up your whole party by itself** (`lib/core/party_share.lua`): every Sidekick session publishes its own party to `config/addons/sidekick/party_<CharName>.txt` — one line per member, `<server_id> <main_job> <sub_job> <main_level> <sub_level> <max_hp> <name>` — and reads every *other* file in that directory, tracking everyone listed there. A healer sitting outside the party therefore needs no setup at all: start both clients and the outside box holds the full party within one 2-second pass, kept in sync as members join and leave. Discovery is a directory listing (`ashita.fs.get_dir`, our own file skipped by name), so there is no host to nominate and nothing to switch on — publishing is unconditional. The file is rewritten only when its text actually changes (join, leave, level-up), not on a timer, and the rewrite goes to a `.txt.tmp` file that is then swapped in (`os.remove` + `os.rename`, since `os.rename` cannot clobber an existing file on Windows) rather than truncating the live one — a reader catching a truncated roster would parse a short-but-valid one and drop the auto targets missing from it, where a reader catching no file reads `nil`, and `nil` never drives a removal. `party_share.cleanup()` deletes the file on unload so a closed session leaves no roster behind. Trusts are left out: they are only targetable by their owner's own party, so they are useless to the box reading the file.

  The roster's real value is what the publisher knows that an outside observer cannot. A player's own client reads job, sub job and levels straight out of its party list, so those columns are facts rather than inferences. Max HP is shipped too, but is **conditional**: it comes from the publisher's own observed-at-100% `member_max_stats` cache, so a member the publisher has not yet seen at full health ships `max_hp` `0`. `common.add_tracked_target(entity, known)` takes the roster as a second argument and **suppresses the `/check`** outright: a check needs the target in range to answer, and comes back just as empty for an `/anon` row, so **`/check` now fires only for targets a human added**. The row is applied by `common.set_tracked_target_info`, which writes job/level and seeds max HP in place of the `AVERAGE_HP_BY_LEVEL[main_level]` estimate — the HP half ahead of its own level guard, since `/anon` hides job and level but never HP. A `max_hp` of `0` is ignored rather than written, so such a row leaves the reader on its level estimate until a later pass carries a real value. `/sk panel` follows: the `~` *HP Values Estimated* marker is driven by a new `max_hp_estimated` field on the tracked snapshot instead of being hardcoded for every tracked row, so a roster-added member shows a plain number as soon as its row carries a real max HP — and a hand-added target drops its `~` too once it has been observed at 100% HP, which is equally exact.

  Auto-added entries are tagged `tracked_targets[sid].auto` and are the only ones the sync ever removes; hand-added targets are never touched. A removal additionally requires that **some** file read back with members that pass, so a pass where nothing read back — every file absent because the owner logged out or unloaded, or a read that caught one mid-rewrite — can never wipe the list. Members are added only once their entity is actually loaded in the reading client, resolved by a **single** scan of the entity table for the whole missing set rather than one scan each, so HP and buff reads are never made against a phantom entry and anyone out of range is simply retried next pass. Our own party members (ourselves included) are skipped — the normal party path already covers them. Thanks to **Kelzalik** for the encouragment to get nerdier.

- **New Pet Control section (PUP/SMN/BST)**: one section (`pet_enabled`, rendered right after **Auto Follow/Attack Range**) holding both pet features as independent checkboxes. **Maneuver** (`maneuver_enabled`, PUP main or subjob) is followed on the same row by three unlabelled dropdowns — one per slot, listing the element alone (`Fire`, `Ice`, …; settings still store the full `Fire Maneuver`) — and Sidekick keeps the picks applied, stacking duplicates if you choose the same element in more than one slot and holding off while **Overload** is up. Beside it, the send-pet-at-target toggle (`pet_control_enabled`, opt-in, off by default) is labeled with the job's *own* ability rather than a generic feature name — **Deploy** on PUP, **Assault** on SMN, **Fight** on BST — and is independent of Maneuver (PUP's used to be coupled to it). It fires only while the pet is **not already engaged**, read off the pet entity's `Status` (`1` = engaged) — the same field `common.is_engaged()` reads off the player. There is no client-side field naming what another entity is targeting: an entity's `TargetIndex` is its *own* slot in the entity array, which is what `refresh_game_state` feeds to `GetLocalPositionX` for the pet's position. A pre-release version read it as the pet's target and resolved the pet itself, so the pet never looked busy and the ability re-fired at the same mob every recast. A `<t>`/`<bt>` dropdown on the same row (`pet_control_target`, default `<t>`) picks which mob: `<t>` is the player's own cursor target and additionally requires being engaged, so a passing hover can't send the pet at something nobody is fighting; `<bt>` is the battle target and needs no engaged check, so the pet joins whatever the party is already on. Jobs store their command with `<t>` and `execute_deploy` rewrites it to `<bt>` when that mode is picked, rather than each job carrying two near-identical entries; either mode also requires the target itself be a live mob, so a targeted party member can't be Deployed at. `pet_enabled` is a real master switch, not just a UI fold: both `pet.execute_maneuver` and `pet.execute_deploy` check it. Both features live together in `lib/actions/pet.lua`, since the send-pet plumbing is infrastructure all three jobs share. **Neither fires while the player has Invisible up** (`common.INVISIBLE_BUFF`, status_effects.sql id 69, now shared with `buff.lua`'s travel-buff gate instead of being a local constant in each): both go out as `/pet`, which drops it. Travel wins over upkeep — maneuvers come back on their own once Invisible is down, a blown Invisible in a mob-heavy zone does not. It bites hardest on the `<bt>` path, which has no engaged check and would otherwise fire while you sneak past a camp toward a party fight. Sneak (71) survives `/pet` and is never gated. `/sk panel` grows a **Status** value on the PET row, so the engaged state that gates the ability is visible.

- **Hold AOE for Group now announces the wait**: while `hold_aoe_for_group` is holding a cast for a missing party member, Sidekick sends `/p Gather together for <ability name>` (e.g. "Gather together for Protectra IV"), so the party knows why nothing is happening. Backed by a new `common.announce_gather(ability_name)`, throttled to once every 5 seconds **across all four hold points combined** (not per-ability), so a straggler doesn't trigger a spam of party chat lines tick after tick. Fires repeatedly (every 5s) for as long as the hold persists, acting as a periodic reminder rather than a one-shot. Wired into all four existing hold points: area songs and `<me>` self-cast AOE buffs in `buff.lua`, fresh Phantom Rolls in `roll.lua` (the hold check there moved to after the specific roll is resolved, so the message names the actual roll being cast), and stratagem-paired AOE spells (Accession/Diffusion) in `common.check_stratagem`. No new setting — inseparable from `hold_aoe_for_group` itself. Thanks to **Toranko** for the feature idea.

- **Per-target Combat/Idle overrides for buff abilities**: right-clicking a **ME**/**P1**-**P5**, alliance (**B0**-**C5**) or tracked (**T1**+) button on any buff row opens a **Combat Only** / **Idle Only** popup scoped to that one target, replacing (not ANDing with) the ability's own Combat Only / Idle Only setting for just that target — e.g. keep Haste on everyone but force it Combat Only for one melee. Session-only, keyed the same way as the existing party-buff config (group name while grouped, else ability name; 0-5 for ME/P1-P5, `al_<flat_index>` for alliance, `tt_<server_id>` for tracked) and never written to settings, so it resets on `/addon reload`. Overridden buttons tint yellow (Combat Only) / green (Idle Only) with a tooltip noting the override. Backed by `common.target_gate_ok` (per-target effective gate, falling back to the ability's own gate via the new `common.ability_gate_ok_now` when no override is set) and `common.ability_gate_bypassed_by_target_override` (keeps `filter_abilities_by_level` from dropping the whole ability when only a per-target override — not the ability's own gate — wants it this tick). The alliance and tracked loops in `buff.lua` run the same per-target check, so an override on a **B**/**C**/**T** button works exactly as it does in the party; with no override they fall back to the ability's own gate, which also keeps a ME/P1-P5 override from dragging an out-of-party target past a gate it never asked to skip. Area songs are the one path with no per-target concept of their own and still gate on the ability's plain setting via `ability_gate_ok_now`. Buff rows only — debuff-removal's na-spell buttons have no automation wired to read this — hidden on buttons that are already locked out (no spell, or an ability that can't target outside the party), and suppressed wherever the ability-level toggle already is (`<bt>`, statically idle/combat-only), so an override can't fight a hard gate. Thanks to **Seikio** for the feature idea.

- **Floating widget — the profile/job and Start/Stop rows on their own** (`/sk widget`, `widget_open`, per character, off by default): a second ImGui window holding exactly the config window's first two rows — the profile button and the job/subjob line, then the Start/Stop button and the automation status line, right-click menus and tooltips included. - **Auto Select for Weather/Day (Red Mage enspells, Scholar storms)** (`lib/core/vanadiel.lua`): a new right-click item on the enspell and storm groups keeps `selected_<group>` pointed at the tier whose element matches the environment, since a matching spell gets a damage bonus. Neither value is exposed by AshitaCore, so both come from FFXiMain.dll signature scans — the weather byte from the signature LuAshitacast and fancycompass already share (`66A1????????663D????72`, byte at `[[sig+0x02]]`, 4-19 → element with odd = double weather, same element either way), the Vana'diel clock from `B0015EC390518B4C24088D4424005068` (`day = floor(([[sig+0x34]+0x0C] + 92514960) / 3456) % 8`).   **Scholar's storms follow a different rule, and the job data says so.** A group whose tiers carry **`auto_element_source = 'weather'`** reads the **zone weather alone** — storms ignored, no day fallback — and its menu item is labelled **Auto Select for Weather** rather than Weather/Day. Both halves are load-bearing for a group that *casts* storms: reading the storm buff would feed the group its own last cast back forever (a Firestorm up would pin the pick to fire no matter what the sky said), and stacking a storm on **matching** weather to double it is the entire reason to chase weather here — so Firestorm under fire weather is the target state, not a redundancy. There is no day fallback because a storm gets no bonus from the day, so with no weather up the user's own pick is simply kept. Storms cover all 8 elements one tier each (Sandstorm 41 → Aurorastorm 48), so Light and Dark weather resolve here where they can't for enspells; the level gate still applies, and a level 45 SCH in light weather keeps its existing pick rather than reaching for the level 48 Aurorastorm.

  No job name or group name is hardcoded anywhere in the module: the 12 RDM enspells and 8 SCH storms gained an **`auto_element`** field (data only, per the job-files-are-data rule) and the feature keys off that alone, so any future elemental group picks it up for free — the menu item appears exactly where an ability carries `auto_element`, and `auto_element_source` on the same entries picks which order it follows. Keying off that name would have hung a dead Auto Select item on every song, bubble and bar-spell in the addon, and — had the two ever been made to compare equal — steered a Bard's Etude and a Geomancer's Indi- selection by the day of the week. Suppressed while the group is ungrouped (`ungrouped_<group>`), where every tier casts independently and there is no single selection to steer.

- **Custom song duration — a level-75 Bard re-sings on a timer instead of waiting for a drop** (`Song Duration (s)` on `/sk panel`, `song_duration` per character, `0`/off by default; `bard.lua`, `buff.lua`, `panel.lua`, `tooltips.lua`): song+ duration gear makes real song length invisible to Sidekick, so party buffs were always reactive — a song had to *drop* before it was recast. With a duration set (BRD main at 75 only), every song Sidekick lands is stamped per target in a `song_expiry` table and re-sung when that many seconds pass, before the real buff wears — set it just under your true duration and songs never drop. Stamping runs a **three-state handshake**, identical for every song — area, party, self, single-target and Pianissimo fast-cast — so no song can hold a timer it did not earn. **ARMED** (`queue_song_stamp`, at send) resolves the target server ids, the only moment we know who the song is aimed at. **STARTED** (`buff.handle_song_cast_start`, on the player's own 0x028 category-8 cast-*begin* for that spell id) confirms the command actually reached the server — refused client-side for silence, range, movement or a changed target it never produces one, so an armed entry alone may never stamp. **STAMPED** (`buff.handle_song_finished`, on the category-4 cast-*finish*) applies the timers, and only for an entry that reached STARTED. Finish is where the buff's duration really starts and where **Troubadour** is read — a cast time earlier it could wear mid-cast and double the timer on a single-length song, an error a full song long in the unsafe direction. Both stages are age-bounded, since a stale entry is exactly how an interrupted song ends up holding a timer: `PENDING_SONG_TIMEOUT` (2 s) on arm→begin stops a later hand-cast of the same song promoting an entry whose command never took, and `PENDING_SONG_MAX_CAST` (20 s) on arm→finish stops a cast that died without an interrupt packet riding a later finish into a timer. A single pending slot is enough since a cast blocks every other send; a cast-begin for a *different* spell drops an entry that is still merely ARMED, while a STARTED one is left alone so a stray player-sourced cast-begin (the mid-cast `/debuff` of a Pianissimo fast-cast) cannot silently cancel the timer. `buff.handle_song_interrupted()` drops the entry on the category-8 interrupt, the category-4 interrupt, a 0x0A zone change (a zoned cast is cancelled without an interrupt packet) and a job change. Timers are keyed by ability name so stacked tiers sharing a buff_id (Ballad + Ballad II) each keep their own; an expired timer bypasses the area pass's held-instance veto, since the old instance it's deliberately overwriting still shows in memory. While a timer is held it is the *only* verdict — buff memory gets no vote, because the instance count reads a shared buff_id in bulk and can't tell which tier a member is short of, so one member missing one March would report every March needed and re-sing them all on cooldown. Timers are therefore disregarded wherever they are known to be wrong. A **landing check** catches a song that resolved without reaching everyone it stamped — an area song stamps whoever was in range at send, so a member who walked out mid-cast would otherwise hold a full timer for a song that never touched them. Each row carries a `verify_at` beside its deadline (`{ deadline, verify_at }`, finish + `SONG_VERIFY_DELAY` = 5 s), and `song_deadline()` checks once on the first read past that point, deleting the row when the song's `buff_id` is absent from that member's buff list. The 5 s delay is what makes the check safe: at finish the song has not posted to the buff list yet (`game_state` is a per-frame snapshot, and the buff array fills from the server's status packet, not from the 0x028 that stamped), so an immediate check would clip every first sing. A **dead member** has their rows deleted outright by `song_member_dead()` and is skipped by both passes, so nothing sings at a corpse and their empty buff list never votes; raised, they hold no timer, so buff memory re-establishes every song at once. Only a trusted read deletes — `build_member_snapshot` falls back to `hpp = 0` on a failed pcall and leaves `entity_status` at its `-1` sentinel, and an out-of-zone member reads 0 HPP too, so HPP 0 counts as death only once the status read succeeded (`entity_status >= 0`, the test `refresh_game_state` uses) — otherwise a transient would throw a live member's timers away permanently. A job change clears the lot via `buff.reset_song_timers()`. The residual cost: a song stripped some *other* way — a Dispel, an Erase-class effect — is not noticed until its timer runs out, which is why the setting wants to sit under your true duration. Buff memory still governs songs no timer is held for — the first sing after a reload, a member who just joined, anyone just raised. Timers are session-local: a reload re-sings everything once to re-establish known deadlines.  Thanks to **Sleazy** for the brainstorming session behind this feature.

### Fixed
- **A stratagem's MP modifier was ignored unless Sidekick had assigned it** (`common.effective_ability_cost`): the function only ever inspected `settings.stratagem_settings`, so a cost-modifying stratagem whose buff was *already up* — the new AOE heal raising Accession itself, or the player simply pressing Accession by hand — was invisible to it. Every other path then budgeted the follow-up spell at its base cost (a Cure IV at 88 MP while the server charged 176), queued a cast the server rejected, and repeated it every tick until MP regenerated or the buff dropped. The nested `pairs(assignments) × ipairs(precast)` loop became a single pass over `abilities.precast` in the process, which is also the only shape that gets the overlap right: under the old nesting a stratagem that was both assigned and active would have been multiplied in twice, turning Accession's 2.0x into 4x. The buff half carries one extra gate the assigned half gets for free — the magic colour / `magic_types` match the **S** popup applies when it *offers* a stratagem, since an assignment can only ever have been made through that popup. - **Song timers outlived the songs themselves, so a member ended up holding neither** (`buff.lua` `handle_song_finished`, `SONG_SLOTS`): the game gives one caster two song slots on one target and overwrites their **oldest** song when a third lands, but `song_expiry` had no eviction model — it only ever grew. Each stale row then suppressed that song's re-sing for its whole duration, so the member sat holding neither the area song (overwritten) nor the single (never recast). A partial guard existed in the other direction only — an area cast dropped every row that was not one of that cycle's `[A]` songs (a `keep` set threaded from `area_song_names()` through `queue_song_stamp()`) — but it fired on **every** area cast including a plain refresh of a slot the caster already held, so it also deleted single-target rows nothing had displaced; with no row, `song_needed()` fell back to buff memory, which still saw the song present, and the single quietly stopped being timer-managed at all. Both directions are now one rule that mirrors the server's: a stamp evicts the oldest row by **start time** (`row.at`, new alongside `deadline`/`verify_at`) until a slot is free, and never for a song already held, since re-singing that is a refresh of its own slot and displaces nothing. Start time rather than time remaining, because Troubadour doubles one song and not the next — the row with the least time left is not necessarily the one the server drops. The `keep` set and `area_song_names()` are gone with it.

- **A song's landing check ran against Trust buff lists, which the same pass treats as unreliable** (`buff.lua` `song_needed`): the verify step deletes a stamped row when the song's `buff_id` is absent from the target's buff list 5 s after the cast finished. For a Trust that list is exactly what `area_needs_recast()` refuses to read — drops go undetected and stacked tiers show as one — so the check deleted good timers, dropped the Trust back to recasting off that same list, and could re-sing on cooldown. `song_deadline()` is now called with `no_verify` for a Trust, so the timer stands as the only thing we have for them. Cost: a Trust that really did lose a song waits out its timer.

- **An area song waiting out its recast stalled every other buff, not just songs** (`buff.lua` `buff.execute`): the normal-mode hold that keeps the single-target pass from singing into a song the area cast is about to overwrite was implemented as a bare `return nil` out of the whole module, so for the length of an `[A]` song's recast the job's non-song buffs — a subjob Protect, Nightingale, a rune — were held too. It is now a `hold_songs` flag that skips only `ability.magic == 'song'` entries in Phase 2. Fast-casting mode is unchanged: it still holds the whole pass on any failure, since Phase 2's songs are blocked by the same silence/MP anyway.

- **Dying left the Bard's own song timers running** (`buff.lua` `buff.forget_song_timers`, `Sidekick.lua`): `song_member_dead()` never sees the player. The tick loop's `common.is_dead()` guard returns before `automation.execute_priority_actions` runs, so nothing evaluates while the body is down, and once raised the read says alive again — so the player's own rows survived a death that had stripped every song they stood for, and a raised Bard re-sang nothing for up to a full duration. The dead branch now drops the player's own rows directly. Only theirs: everyone else's songs outlive the Bard's death.

- **Area songs were never re-sung when only Trusts were left to read** (`buff.lua` `no_readable_voter`, `DEFAULT_SONG_DURATION`, `area_manual`): with `song_duration` at 0 the area pass decides by buff memory, and it deliberately refuses to read the members whose lists lie — Trusts (drops go undetected, stacked tiers show as one), the out-of-zone and out-of-range, the dead, and anyone whose slots are wholly assigned to single-target songs (their own singles overwrite the area song, so its absence proves nothing). When that leaves **nobody**, `area_needs_recast()` can never return true: the area song is never reported missing, never re-sung, and the single-target pass becomes the only thing that sings — which is backwards, since an area song takes those slots back the moment it does fire. `[A]` songs now fall back to a timer at `DEFAULT_SONG_DURATION` (120 s, the base song length) whenever that happens. The fallback is **scoped to area songs alone** via a separate `area_manual` flag: single-target songs land on members whose lists we can read, so memory is a fine fallback for them, and putting a duration-geared Bard's own songs on a guessed 120 s clock would re-sing them a minute early — which is what **Song Duration (s)** exists to prevent. Setting a duration still governs every song, area included.

- **A single-target song evicted the area timer that was scheduling the group's re-sing** (`buff.lua` `slot_locked`): on a member whose slots are wholly assigned to single-target songs, the area row is a re-sing **schedule** for the whole group, not a claim the song is on that member — it is not, their own singles overwrote it, which is why the landing check already skips them. Letting a single-target stamp evict it left the area pass reading *slots full, no timer held* and recasting on cooldown, the exact spam these timers exist to stop. Those members are now exempt from eviction, so `/sk panel` can legitimately show more rows for them than a Bard has slots: real buffs plus schedule markers.

- **A dead party member forced area songs to recast on cooldown** (`buff.lua` `song_member_dead`, `area_needs_recast`, `buff.execute`): death strips every buff, so a corpse's buff list reads empty and the area pass had no notion of death. With manual song timers off it simply saw a member missing every song and re-sang on cooldown, re-establishing — and, with timers on, restamping — everyone else's songs each cycle for as long as the body lay there; with `song_duration` set, `song_deadline()` reported no timer for a corpse, which fell straight through to that same buff-memory check and produced the same spam, while the single-target pass sang at the body. `song_member_dead()` now drops every timer held for that member and both passes skip them until they are raised. Raised, they hold no timer, so the memory check governs and every song is re-established at once. Only a trusted read counts as death: `build_member_snapshot` falls back to `hpp = 0` on a failed pcall and leaves `entity_status` at its `-1` sentinel, and an out-of-zone member reads 0 HPP as well, so HPP 0 is death only once the status read succeeded (`entity_status >= 0`, matching `refresh_game_state`) — out-of-zone members fall through as not-dead and are excluded by the zone gate both passes already apply.

- **Zoning with the config window open deselected spells** (`ui_config.render`): a zone blanks the player memory block, so for the frames behind the loading screen `HasSpell` reads false for *every* spell and the player level reads 0. The render path treats that as "you don't know this spell" and writes the conclusion back to settings — `ability_checkbox` setting `disabled_<name> = true`, `disable_uncastable_songs` dropping song target selections — so a zone line could clear every cure and song the user had ticked, permanently. `ui_config.render` now returns early while `common.is_loading()`, which costs nothing: the window is behind the loading screen and invisible for those frames anyway.   Thanks to **Kelzalik** for reporting the bug.

- **Red Mage Flurry was never detected as up, so it was recast on every buff pass** (`red_mage.lua` `abilities.buff`): the entry carried `buff_id` 265, which is what `status_effects.sql` names `flurry` — but CatsEyeXI does not apply that status for the spell. Its `scripts/globals/spells/enhancing_spell.lua` maps **both** Flurry (spell 845) and Flurry II (846) to `xi.effect.FLURRY_II`, id **581**, with an explicit `-- Thats the actual effect. Not a typo.` beside each row; status 265 is defined but unused by the spell. `action_core.has_any_buff` therefore never found 265 on the target, the buff read as missing every tick, and Sidekick recast Flurry at 40 MP forever — refreshing a buff that was already up and holding the rest of the buff queue behind it, since a buff that can never be satisfied is always the next thing to cast. The entry's `buff_id` is now 581. `common.BASE_BUFF_DURATION`'s `['Flurry'] = 180` is unaffected: that table is keyed by spell/buff *name* for packet-tracked targets, not by status id. Thanks to **Swizz** for reporting the bug.

- **Amnesia did not block pet commands** (`common.is_command_blocked`): the gate matched `^/ma ` for Silence and `^/ja ` for Amnesia and nothing else, so every ability a pet job issues through `/pet` sailed straight past it — Puppetmaster's eight Maneuvers and Deploy, Beastmaster's Ready moves and Fight, Summoner's Blood Pacts, Avatar's Favor, Shining Ruby and Assault. All of those are job abilities server-side, so Amnesia rejects them exactly as it does a `/ja`, and Sidekick spent the 1.1-second action throttle re-sending one every tick for the full duration of the status. The `elseif` now matches `^/pet ` alongside `^/ja `. One edit covers every caller: `is_command_blocked` is the first step of `action_core.is_usable`, and `try_use`, `first_command` and `filter_usable` all route through `is_usable` — so `pet.execute_maneuver`, `pet.execute_deploy`, `heal.execute_pet` (which is where BST Ready moves are served from), `status_removal.execute_pet_debuff_removal` and the pet self-buffs in `buff.execute` were fixed by the one line. The stale comment in `pet.execute_maneuver` documenting the hole went with it. `/item`, `/heal` and `/follow` stay deliberately unmatched: Amnesia blocks none of them.

- **Sleep, Stun, Terror, Petrification and Charm did not stop automation at all** (`common.INCAPACITATING_STATUS` / `common.incapacitated_by`, `Sidekick.lua` `automation_tick` and `follow_tick`): nothing anywhere checked for them. The tick loop's guards cover loading, mounted, dead, can't-attack and casting — and `common.can_attack` only reads the zone id against the non-combat list plus the event-system pointer (cutscene/dialog), while `common.is_dead` only tracks KO — so a slept, stunned or terrorised player read as perfectly able to act. Sidekick kept serving commands the server refused outright, one per 1.1-second throttle, for as long as the status lasted.

  `common.INCAPACITATING_STATUS` now maps the statuses that stop the player acting *at all* — Sleep (2), Petrification (7), Stun (10), Charm I and II (14 / 17), Sleep II a.k.a. Lullaby (19), Terror (28) — to the label printed in the debug log, and `common.incapacitated_by` returns the first one found on the player, or nil. `automation_tick` returns on it immediately after the dead guard; `follow_tick`, which runs its own guard chain whenever the engine is stopped or paused, returns on it too, since none of these leave the player able to move either. Gradual Petrification (18) is deliberately absent — it is a countdown to status 7, not a lockout, and the player acts normally until it lands. Doom, Addle and Weakness likewise block nothing.

  **The check sits in the tick loop rather than in `is_command_blocked`**, and that placement is the point. That function is a per-command-*family* gate (Silence on `/ma`, Amnesia on `/ja` and `/pet`) reached only from `action_core.is_usable`; these statuses block everything, including the paths that never touch the ability pipeline — `item.execute`, `rest.execute`'s `/heal`, and the Multisend range/follow handling further down the same tick. Returning from the tick covers all of them and reads the player's buff array once per frame instead of once per candidate ability. The pause is logged once per onset (`last_incapacitated`), not once per frame.

- **Mute did not stop spellcasting** (`common.has_silence`): Mute (status 29) blocks magic exactly as Silence does, but it is a separate status — Silena will not touch it — and the gate only ever tested status 6. `has_silence` now returns true for either, so `/ma` commands are held under Mute as well. It reports as `Silence` in the debug log rather than gaining a reason string of its own; the two are one block as far as the pipeline is concerned.

- **`is_combat` holds through a grace window after the battle target vanishes** (`common.is_combat`, `COMBAT_GRACE = 5.0`s): a multi-mob pull has no `<bt>` for a moment between one mob dying and someone engaging the next, which flickered every `combat_only` ability off and every `idle_only` ability on for a tick or two. `is_combat` now stamps `os.clock()` on each real battle-target read and stays true for `COMBAT_GRACE` seconds after the target disappears, so support coverage overlaps the dead-mob → next-mob gap instead of thrashing. `is_idle` inherits it (it's the negation).

### Fixed
- **Scholar Arts MP tax was ignored** (`common.arts_adjusted_cost`, applied through `common.effective_ability_cost`): an Arts stance taxes the **opposite** magic school by 20%, so under Dark Arts a Cure IV really costs 105 MP, not 88 — Sidekick budgeted the untaxed number, queued the cure, and ate the server's rejection. The tax is keyed off the spell's `Type` from the resource manager (1 white / 2 black) rather than a hardcoded spell list, so it covers subjob spells for free and never touches ninjutsu, songs, summoning, blue, geomancy, JAs or items. Three details come straight from `battleutils::CalculateSpellCost`: it adds as `cost += (int16)(base * mod / 100.0f)`, a C cast, so the tax **truncates** and never rounds up; **Tabula Rasa** (377) suppresses it entirely (`light_arts.lua` / `dark_arts.lua` skip the `+20` mod while TR is up, and `tabula_rasa.lua` subtracts 30 from that same mod); and a cost-modifying stratagem **replaces** the tax instead of compounding with it, since Penury/Parsimony/Accession/Manifestation all clear `applyArts` server-side. That last one is why a Penury'd Cure IV in Dark Arts is 44 MP and not 53. Whether a stratagem applied is tracked by a flag rather than `modifier ~= 1.0`, since Accession 2.0x × Penury 0.5x multiplies back out to 1.0 and still suppressed the tax.
- **Accession cost was 3x, the server charges 2x** (`scholar.lua`, `mp_modifier`): `battleutils::CalculateSpellCost` does a plain `cost *= 2` for a `SPELLAOE_RADIAL_ACCE` spell under Accession, matching the ability's own description ("MP cost is doubled"). The 50% overestimate made Sidekick skip Accession'd cures it could afford.
- **Accession was offered on spells it cannot extend**: matching the stratagem's colour (`magic = 'white'`) and `magic_types` was too coarse — the server extends a spell only when its `spell_list.sql` `AOE` column is `4` (`SPELLAOE_RADIAL_ACCE`), so Raise/Raise II/III/Arise, all four Reraise tiers, Haste/Haste II, Flurry, Cure V/VI, Temper, Gain-\*, Crusade and Sacrifice are untouched by it, as are the lines that are already AoE on their own (Curaga, Cura, Esuna, Boost-\*, Hastega). Sidekick would still burn the charge, double the budgeted MP and drop the Arts tax that in fact still applies. Precast entries gain an optional `spell_ids` allowlist (Accession's is copied from `spell_list.sql`) enforced by the new `common.stratagem_applies(strat, ability)`, which gates all three consumers together: the **S** popup no longer offers it on those rows, `effective_ability_cost` no longer applies the modifier, and `check_stratagem` no longer fires the JA. A stratagem with no `spell_ids` behaves as before.
- **Ability MP costs displayed in the UI could disagree with the cost the automation gated on**: `components.lua` carried its own `get_stratagem_mp_modifier` keyed on the group name, while `common.effective_ability_cost` prefers the ability name and falls back to the group — so a per-ability assignment showed one number and gated on another. The duplicate is deleted; all five display sites (group dropdown current + list, self single, party single, ability checkbox) now call `effective_ability_cost` directly, which also gets them the Arts adjustment for free.
- **Entrust fired without the MP to follow it**: the Indi spell's MP cost was only checked in the branch that casts it, so with the Entrust buff already up Sidekick would pop **Entrust** (5 minute recast) and then sit unable to afford the Indi spell. The cost check is now hoisted above the buff branch in `geo.lua`, gating the JA and the follow-up cast alike. Thanks to **Tai** for reporting the bug.
- **Follow's packet guard wiped the job-mastery stars and the GEO Indi aura** (`Sidekick.lua` `packet_in`): the autorun-cancel guard zeroed 0x37 byte 0x58 on every player-update packet while `follow_enabled`, but that byte is not a movement flag — it is `Flags4`, carrying the GeoIndi aura bits (0-6) and `JobMasterFlag` (bit 7). Zeroing it stripped the master stars from the nameplate and killed the Indi aura visual whenever Follow was on. The 0x37 write is deleted outright; the 0x0D byte 0x42 zeroing — the byte that actually carries the server's autorun-cancel — remains and is sufficient to keep `/follow` alive across position syncs. Thanks to **Morwen** for reporting the bug.
- **Alliance members didn't appear in the config UI until automation was started**: the alliance B/C selection buttons render from the `common.game_state.alliance` snapshot, but `refresh_game_state()` only ran from the automation tick (gated on `automation_enabled`), the follow tick (gated on `follow_enabled`), or the `/sk panel` render — so with automation stopped, follow off and the panel closed, the snapshot froze and a newly joined alliance member never got a button until Start forced a refresh. The P1-P5 buttons were immune, reading the party manager live. `ui_config.render` now runs the same staleness-guarded refresh the panel already used (skip if refreshed within 0.1 s), so the config window keeps the snapshot current while open at no cost when automation is running. Thanks to **Tai** for reporting the bug.

- **Blue Mage spells were wrongly locked behind Unbridled Learning** (`blue_mage.lua`): Battery Charge, Animating Wail, Magic Barrier, Occultation, Orcish Counterstance and Barrier Tusk carried `requires_precast = 'Unbridled Learning'`, so Sidekick popped the JA before every cast and skipped the spell whenever Unbridled Learning was on cooldown — even though on CatsEyeXI those six cast normally. Only Harden Shell, Pyric Bulwark and Carcharian Verve actually need the precast; the flag is now scoped to those three. Those three are also **exempt from the set-spell equipped check** (`common.is_blue_magic_unequipped` returns false for any `requires_precast = 'Unbridled Learning'` spell): Unbridled Learning unlocks them via the JA rather than the equipped blue-magic list, so they were being grayed and skipped as "not currently equipped" even though the automation would have cast them fine. All 25 BLU `spell_id`s were re-verified against `spell_list.sql`. Thanks to **Benthere** and **Muziko** for reporting the bugs.

### Changed
- **Party State Panel Upgrade** `/sk panel` reorganized and styled.

- **Ability ordering via `priority`**: `common.filter_abilities_by_level` now sorts the available-ability list by an optional `priority` field (descending) before the existing cost-descending tiebreak, so an ability can be forced ahead of others regardless of MP cost. Unset reads as 0, leaving every other job/section unchanged. It applies to any action type routed through that filter (`buff`, `heal`, `heal_pet`, `recover_mp`, `recover_tp`, …), which matters most after main/sub ability merging — e.g. **SAM Meditate** and **DNC Reverse Flourish** (100) each outrank whatever a subjob contributes to the same `recover_tp` list. Used where cast order matters within a tick: **RDM Composure** (100) casts before its other self-buffs so their durations inherit the Composure bonus; **SCH Sublimation** (50), the **GEO** Indi/Geo self-buffs (50), **BLU Battery Charge** (50) and **RUN/RDM Refresh** (50) sort ahead of their lower-priority peers, with **RDM/WHM Haste** and **RDM Flurry** (25) below them; **GEO Radial Arcana** (90) is preferred over Aspir; **PUP Repair** (100) is preferred over Role Reversal. Do **not** set it on a grouped tier — `buff.lua`'s default-tier auto-select casts the first grouped tier it sees expecting highest cost first, and a per-group special-case would make the comparator intransitive (sort crash), so `priority` stays off grouped abilities. Thanks to **Plush** for the feature idea and code.

- **Command throttle times from an action's completion, not its send** (1.0 s → 1.1 s, matching the game's server-side post-action lockout). The lockout runs from when the server *resolves* an action, but `execute_command` can only stamp on send — a whole cast time early for a spell, so the stamp expires mid-cast and the next command fires into the lockout and is eaten. `automation.notify_action_finished()` re-stamps from the player's own 0x028 finish packets (`ACTION_FINISH_CATEGORIES` in `Sidekick.lua`: 2/3/4/5 ranged/WS/spell/item, 6/14/15 job abilities; the `*_begin` categories 7/8/9/12 are excluded, since each has its own finish packet later — unless the begin carries `INTERRUPT_PARAM`, which `is_action_finish` accepts because a cancelled action never sends a finish and locks out just the same). Only ever moves the stamp later, never earlier. Also catches actions the **player** took by hand, which `execute_command` never sees.

- **Spells carry a longer completion lockout in the command throttle** (1.1 s → 3.1 s, spell finishes only). A spell's server-side post-cast lockout is longer than a job ability's or item's, so `automation.notify_action_finished(is_spell_finish)` stamps the extra seconds forward when the resolving 0x028 is category 4 (`spell_finish`), while ranged / WS / item / JA finishes keep the 1.1 s gap. The throttle check always subtracts `command_throttle`, so a stamp pushed `(spell_finish_throttle − command_throttle)` into the future yields the full 3.1 s gap. Stops the next command firing into the tail of a spell's lockout and being eaten. An interrupted spell arrives as its `*_begin` category (not 4) and correctly keeps the short 1.1 s gap.

- **Removal spells no longer loop on Trusts/tracked/alliance/pet targets, and a resisted cure retries instead of orphaning the status**: These targets give no reliable wear-off packet, so after Sidekick cast e.g. Poisona the tracked Poison lingered and the cure re-fired every tick. On casting a na-/Erase spell — including a pet Reward/Maintenance strip — `common.drop_removed_debuff` now marks one matching status as **in-flight** for `REMOVAL_SUPPRESS_WINDOW` (~4 s) rather than deleting it outright: `common.removable_after_suppression` hides it from the removal selector while the cast resolves (no loop-casting), a landed cast's removal packet (`0x028` msg-83 / `0x029` wear-off) clears it for real inside the window, and a rejected/resisted cast — which sends no packet — lets the mark expire so the status becomes eligible again and is retried, instead of vanishing from tracking while still on the target. Each removal clears one status per cast; the debuff base-duration timer catches anything guessed wrong, and the panel keeps reading the full tracked list.

- **Casting detection rebuilt on parsed 0x028 categories**: the old detector probed raw bytes (actor id at `0x05`, "completion flag" at `0x0F`). Now reads `parse_packets.parse_action_packet` — category 8 `casting_begin` sets the lock, 4 `spell_finish` clears it, 1 (melee) is dropped since an autoattack says nothing about casting.

- **Interrupts read straight from the packet**: an interrupted action sends no finish packet. It repeats its own `*_begin` category (7 WS / 8 casting / 9 item / 12 ranged) with `Param` replaced by `28787` (`0x7073`) where the spell/ability id would be — now `common.INTERRUPT_PARAM`, and no real id collides with it. Three readers key off it. `handle_action_packet` ignores that second category 8 instead of treating it as a fresh `casting_begin`, which re-armed the cast lock and froze automation until the timeout. `is_action_finish` (`Sidekick.lua`) restarts the command throttle from an interrupted `*_begin`, since the server locks out the same whether the action landed or was cancelled. `get_last_action` reports `interrupted (casting_begin)` rather than a bogus cast plus a spell lookup on an id that isn't one. `cast_timeout` 5 s → 16 s: with interrupts detected and zoning clearing the lock explicitly, the backstop now covers only a genuinely missed packet.

- **Debug panel shows `Action:` instead of `Casting: true/false`**: `common.get_last_action()` names the last 0x028 category seen from the player (`casting_begin: Cure IV`, `job_ability`, `ws_finish`, `interrupted (casting_begin)`, …), so a cast is watchable start-to-finish. Melee isn't recorded (it'd drown everything else while engaged); the spell name resolves only for categories 4/8, where `Param` is a spell id. Reads `none` before the first action, after the stuck-cast timeout, and after a zone change.

- **Ability id fields split into `spell_id` / `recast_id`**: the single `id` field is gone. `spell_id` (`spell_list.sql` `spellid`) is used by `/ma`, `recast_id` (`abilities.sql` `recastId`) by everything else, and the *field name* — not the command text — now selects which recast table `action_core.is_usable` reads. Replaces the old `is_spell_command` command-sniffing helper. Each ability carries exactly one. Item/ammo tier tables (BST `PET_FOOD`, NIN `SHURIKENS`, PUP `OILS`) keep their bare `id` (item ids, not abilities).
